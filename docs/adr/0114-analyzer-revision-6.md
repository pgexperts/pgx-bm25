# 0114. Analyzer revision 6, a per-encoding word-class table for single-byte databases and a dictionary-output probe in the fingerprint

## Context

Two analyzer defects were found by the 2026-10-04 review. Both change what a stored
fingerprint says, so they share one revision bump and one REINDEX (the user's decision of
2026-10-05).

**#295.** Since ADR 0077, run splitting in a single-byte database tested
`c < 0x80 && isalnum(c)`, so every byte `0x80` to `0xFF` was a separator. Cyrillic in
WIN1251 or KOI8-R tokenized to nothing: `CREATE INDEX` succeeded with zero recall.
Accented LATIN1 words split into fragments that cross-matched (`'Aerger'` matched
`'Der Buerger zahlt'`). SQL_ASCII shredded every non-ASCII character the same way. ADR
0077 had removed the `LC_CTYPE` call because `LC_CTYPE` is recorded nowhere the
fingerprint can see.

**#296.** The fingerprint covered the dictionary's name and configuration but said nothing
about what it does. A stemmer that changed under an unchanged name passed the gate and
the index silently missed rows. PostgreSQL 18's Snowball update changed six English stems
(`added` and `adding` went from `ad` to `add`; `egging`, `erring` and `offing` likewise),
and an in-place `ALTER TEXT SEARCH DICTIONARY` does the same. ADR 0080 had made the
identity the schema-qualified name and template, which cannot see either.

## Decision

**Word-class table (#295).** In a single-byte server encoding a high byte is a word byte
if and only if a fixed per-encoding 128-bit table says the encoding maps it to a letter or
a digit. The table, `src/bm25_sb_wordclass.c`, is generated by `ci/gen_sb_wordclass.py`
from PostgreSQL 18.6's conversion maps (`src/backend/utils/mb/Unicode/*.map`; LATIN1 is
the identity) and `pg_u_isalnum(code, posix = false)` at Unicode 16.0, which is the
Alphabetic derived property or general category Nd. It is committed, and deliberately not
regenerated by the build or CI.
- Unmapped bytes are separators.
- SQL_ASCII is not tabled: its high bytes are word bytes, as in a multibyte encoding.
- UTF-8 and other multibyte databases tokenize byte-identically across the bump.
- Case folding is unchanged, at core parity: `C` collation does not lower-case non-ASCII
  letters, as in core.
- The snippet edge walkers use the same predicate. In a single-byte encoding a byte is a
  character, so the table predicate is correct for the backward walk.

**Dictionary probe (#296).** Fingerprint component 7 is a 32-bit FNV-1a of the output
of bm25's own fold (`bm25_fold_term`) and the resolved dictionary's raw `lexize` over a
fixed probe word list, with the words fed to `lexize` in their original case as ingest
does. Non-ASCII probe words are included only in UTF-8 databases. The hash is cached per
backend by dictionary OID and invalidated by a `TSDICTOID` syscache callback, so an `ALTER`
is seen by the next statement in the same session and the per-row ingest gate stays a hash
lookup. Raw dictionary output is hashed, with a stopword drop recorded as an empty result,
rather than applying the `stopwords` reloption, which is already component 3; that keeps the
dictionary OID a sufficient cache key.

**One bump.** `BM25_ANALYZER_REVISION` goes from 5 to 6. For a single-byte database this
is a genuine tokenization change, so `require_analyzer_match = false` is not a safe way to
defer the REINDEX. For every other database the stored segments are still correct and the
REINDEX only restamps, unless the index crossed a `pg_upgrade` whose stemmer changed,
which is what the probe now detects.

**What the gate now catches.** A collation or library upgrade that changes a probe word's
fold or stem trips the gate (REINDEX). One that changes nothing the probe covers still
passes, which is the benefit ADR 0080's name-derived identity introduced. README and
ARCHITECTURE say so, and the false "pg_upgrade cannot change tokenization" premise in the
`bm25_analyzer.c` header is corrected.

**Tests.** `t/026_single_byte_encodings.pl` (WIN1251, KOI8R, LATIN1, SQL_ASCII, plus a
UTF-8 control) and `sql/132_dictionary_probe` (stoplist and stemmer ALTERs trip the scan
and ingest gates in-session; `require_analyzer_match = false` proceeds; reverting restores
the fingerprint; REINDEX restamps).

**`bm25_buildempty` lock order.** The probe made a pre-existing violation of the house rule
(no catalog work under a buffer content lock) heavier: `bm25_buildempty` reserved the
init-fork metapage, which `bm25_meta_extend` returns EXCLUSIVE-locked, before opening the
heap and computing the fingerprint. The reservation now follows all of that catalog work
and the probe; only the field-config page has to follow the reservation. See ADR 0042's
addendum.

## Alternatives considered

- **`isalnum()` under the locale.** What ADR 0077 removed, because `LC_CTYPE` is not in the
  fingerprint.
- **`pg_do_encoding_conversion`.** It resolves the conversion through `pg_conversion`, so a
  `CREATE DEFAULT CONVERSION` on `search_path` could change the answer: an environment input
  the fingerprint does not record.
- **The server's `pg_u_isalnum` at run time.** PostgreSQL's Unicode tables move with the
  major version (17: Unicode 15.1, 18: 16.0, 19: 17.0), so one byte could change class across
  a `pg_upgrade` with nothing to detect it. Pinning the table in this repository makes
  changing it an analyzer revision bump like any other output change.
- **Mix the new revision into the fingerprint only for single-byte encodings**, to spare
  UTF-8 users the REINDEX. The user accepted the REINDEX for everyone, as the revision 4 and
  5 bumps did, so the 7th component and the table ride one event.
- **Put `PG_VERSION_NUM / 10000` in the fingerprint.** Sound, but it restores pre-0080
  behaviour (every `pg_upgrade` is a REINDEX) and voids ADR 0080's benefit. The issue
  allowed it only as a fallback.
- **A WARNING at `CREATE INDEX` on a single-byte encoding** as an interim, if the table work
  were deferred. Not needed once the table landed.

## Consequences

- Every existing index needs one REINDEX on upgrade (revision 6). README carries the
  release note.
- A thesaurus configured as `<lang>_stem` now fails at `CREATE INDEX`, even on an empty
  table, because the probe lexizes it. It already failed at ingest ("forbidden call of
  thesaurus or nested call", ADR 0087), so this changes when it fails, not whether.
- **Residual:** in WIN1258 and WIN874, a combining mark the generator does not classify as
  Alphabetic or Nd is a separator, so decomposed text splits at it. In WIN1258 these are
  the combining accents (bytes `0xCC`, `0xD2`, `0xDE`, `0xEC`, `0xF2`), so decomposed
  Vietnamese tokenizes into fragments; in WIN874 they are Thai tone and similar marks
  (`0xE7` to `0xEC`, `0xEE`). Not a regression: every high byte was a separator at
  revision 3 to 5.
- The probe sees only what its word list touches. A behaviour change confined to other
  words stays invisible, as does a 32-bit hash collision.
- Nothing pins the 17 to 18 probe words in a test.
